# 关联任务批量查询与重新关联补修 · 2026-11-15

本轮针对个人实例中 256 项关联任务出现数千次数据库读取的问题。计数覆盖任务启动、上下文准备、检索、提交检查、模型用量结算、关联保存与检查点；主 SQLite 和向量 SQLite 合计，包含 SELECT / WITH / PRAGMA。建造测试资料、入队和完成后的查询报告请求不计入任务。写入及提交次数另计，不把减少读取等同于减少全部 SQL。

## 实现

- Studio 与 Compose 默认启用 `VKS_PERSONAL_MODE=1`。个人扫描/关联任务内部直接采用实例所有者，省去逐项身份、成员及能力判断；Web/MCP 入口仍使用共享服务。任务 attempt、lease、取消、准确资料版本、模型配置、人工修改和用户移除检查保留。普通服务默认值和共享模式回归仍关闭个人模式，显式设置 `0` 可恢复共享模式任务检查。
- 就绪读取与保存分别共享当前事务快照。项目、草稿、任务、工作区、模型策略和选择映射一次加载；资料事实可按变更版本复用，当前选择与保存前检查仍在本次事务内读取。
- 目标、关系、证据、用量、幂等键、文档身份及准确文档修订批量预取，包含不存在的目标。一个批次中跨文档的完整章节映射用一次聚合 SQL 验证，不逐份装载全部章节正文；错误映射只影响对应条目。
- 查询向量按独立 key 批量读取，当前批次复用配置、授权资料快照和精确向量矩阵，评分在读取事务之外执行。各目标保留自己的查询向量、候选和排序，不混合向量、不共享最终答案、不减少 Top-K。未命中的嵌入在事务外生成。
- JSON / Schema 校验在保存队列之外执行；重复的响应后读取并入同一保存事务。用量预留不占用本地准备槽。默认模型并发 128、保存批次上限 32，执行时间片 250 ms；没有把网络模型请求放入 SQLite 事务。

## 合成查询预算

256 个独立目标、8000 输出上限，模型响应与 64 维嵌入均使用本地模拟；有向量的新建场景包含本轮冷建库。重新关联先建立同样的 256 项已有结果，再只计重新关联任务。16 文档场景使不同目标引用不同候选文档，避免单文档夹具掩盖跨文档 N+1。

最终全量回归中的合成验证如下。调度会使批次数及查询数小幅变化，回归门槛逐场景固定为主库加向量库 **少于 1000 次**：

| 文档数 | 向量 | 操作 | 主库读取 | 向量库读取 | 合计 |
| ---: | --- | --- | ---: | ---: | ---: |
| 1 | 关闭 | 新建关联 | 236 | 42 | 278 |
| 1 | 关闭 | 重新关联 | 459 | 36 | 495 |
| 1 | 开启 | 新建关联 | 488 | 190 | 678 |
| 1 | 开启 | 重新关联 | 521 | 81 | 602 |
| 16 | 开启 | 新建关联 | 520 | 191 | 711 |
| 16 | 开启 | 重新关联 | 612 | 82 | 694 |
六组均保存 256/256 项，模拟模型请求各 256 次。完整映射验证包含重复 ID、缺失修订、数量错误、跨文档、错误 artifact、错误类型及同身份多个修订等破坏场景；批量验证保持逐项拒绝。映射与查询预算专项共 15 项通过；额外验证其他服务直接更新根实体后缓存会立即失效。

相同生产源码的完整分片复跑中，六组分别为 279 / 495 / 638 / 854 / 702 / 652 次读取，也全部低于 1000。最终两轮查询预算范围为 278–854，不能将批次调度差异当作检索结果差异。

这是合成回归证据，不是用户全部真实资料的查询数或速度保证。此前真实 256 项的 23.229 秒属于上一版保存优化，不能当成本轮实测。本轮按用户要求暂停真实模型与真实资料性能重放；因此不宣称本轮已达到整体 10 倍、5 秒保存或真实质量非劣。

## 提示词重新关联

- 在“相关文档”触发重新关联后留在当前页签；失败与重试保留原目标、提示词和页签，重试仍调用重新关联接口，不转为普通讲解。
- 关联文案成功后直接更新相关文档区；失败保留已有结果，并明确显示保留状态。
- 显式重新关联允许 120 秒网络等待，8000 输出上限不变。网关区分超时、连接断开、连接错误及非法 JSON；不自动重放可能已经提交的 POST。
- 独立浏览器合成回归验证首次 503 后原地重试、相同提示词和接口、更新文案，以及原有问答修改/导出路径。未调用真实模型。此前线上 503 没有足够分类日志，不能据此断定它一定是超时或本轮已消除所有供应商错误。

## 企业场景中的批量检索

后台扫描与批量关联适合合并传输及数据库读取，每个查询仍独立计算和返回结果；单次交互优先低延迟，不应为了凑批长时间等待。企业多租户部署必须保留租户、权限和版本过滤，不能套用个人模式省略任务鉴权。原生批量 API 是否提供多查询能力取决于数据库；SDK 并发封装不一定减少服务端请求数。

官方接口示例：[Qdrant 多查询批量接口](https://api.qdrant.tech/api-reference/search/query-batch-points)；[Pinecone Python 性能说明](https://sdk.pinecone.io/python/guides/performance.html)说明批处理封装中各查询仍可独立往返，需按实际提供方能力区分。

本项目先保留 SQLite 与精确评分，通过批量 I/O 和当前事务复用减少往返。不把查询拼成一个向量；不因大上下文默认合并模型推理。模型推理合批仍受此前独立质量验证门槛约束。
