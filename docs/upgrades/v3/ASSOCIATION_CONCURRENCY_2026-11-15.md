# 关联并发、异步处理与批量保存

2026-11-15。接续[上一轮性能记录](ASSOCIATION_PERFORMANCE_2026-11-15.md)。本轮优化以同一真实资料、同一模型及 8000 输出上限进行；保留原任务输入、已有不可变修订、人工说明及检查点。

## 同步链路

- 浏览器仍为 1–4 路。模型请求由实例变量 `VKS_AI_CONCURRENCY` 独立设置，默认 64，范围 1–128；全部 API、Worker 进程必须使用同一值。1 路保留串行诊断行为，2–4 路使用实例模型容量。全量任务和逐页任务继续通过数据库租约共享容量，不是各自再开一套池。
- 本地准备最多 8 个任务同时进入。准备、模型网络请求、结果核对、写入分别调度，返回网络响应即释放请求槽。生产继续发送原来的独立控件提示词，不合并模型答案，不减少候选片段或讲解要求。
- 已就绪的准备、发送前检查和响应核对按最多 32 项共享一个当前只读事务。权限、模型策略、资料组合和完整准确输入只在该事务内复用；新批次必须重新读取。控件身份和候选集合各自保留。
- JSON 解析、Schema、引用范围和响应资料核对放在写入事务之外。实际保存时仍在写事务中复核准确输入、当前授权、任务 attempt/lease、取消、工作区、人工说明及目标修订。

## 批量写入与最终一致性

`VKS_AI_SAVE_BATCH_SIZE` 控制每次最多合并多少项，默认 32，范围 1–128。准备好的预算预留优先处理；普通结果最多收集 250 毫秒。单个写事务处理约 250 毫秒后让出队列，避免长批次占住人工编辑。批量值是上限，并不保证每次凑满。

同一事务内，每项使用独立保存点。单项拒绝不会撤销其他项；真正提交失败则该批不能确认成功。模型预算预留实际提交后才发送网络请求，结果实际提交后才进入内存复用缓存。进度、覆盖率展示及任务检查点通过后台队列合并更新，事务结束时只生成一次该批最新进度；每个目标仍保留独立持久检查点。

全量任务中的临时失败会通过既有数据库 outbox 创建一次仅包含失败目标的后台修复任务。旧任务及其检查点保持历史结果，成功目标不重复生成；修复任务不再递归重试。无充分资料、用户移除、人工内容、取消、权限或资料基线冲突不自动重试。逐页扫描仍沿用原扫描范围与已完成目标，未引入自动整库重扫。

## 具体热点

1. 引用归属核验从“加载文档的全部章节正文和 ORM 对象”改为 SQL 对完整准确映射一次计数和去重核验。项目、实体类型、原始 artifact、document_key、完整成员数及章节逻辑身份唯一性全部检查；只返回所需引用。没有准确映射的旧文档继续使用原解析器。没有把全量核验改成仅看一个引用是否存在。
2. 草稿当前选择使用 SQLite JSON 聚合读取，与原标量映射完全一致，仍读取当前事务，不跨事务缓存可变选择。
3. 向量用 NumPy 本地计算缩小候选范围；临界分数、并列结果和非标准旧向量用原 `math.sumprod` 精确复算，保留候选、顺序和融合逻辑。缓存仅含当前授权修订的事实，向量库触发器 epoch 在跨进程增删改时失效，内存预算 128 MiB。
4. 模型 HTTP 连接可复用。每次请求仍重新校验出站策略与 DNS/IP；地址、SNI 或凭据身份变化不借用旧连接。完整读取且成功的响应才归还连接，不自动重放不确定的 POST。
5. SQLite 文件库启用 WAL，继续使用 `synchronous=FULL`；不牺牲已确认保存的落盘可靠性。内存库保留原 journal。备份仍需一致快照，不能只复制活跃实例的主数据库文件。

## 验证边界

性能对照使用当前实例的一致副本和原任务的 256 个独立目标，不重置在线任务。检查模型、完整请求体、8000 上限、候选、准确引用、持久检查点及已保存结果。原始材料、逐项响应、私有数据库和计时位于忽略目录 `.vks/concurrency-20261115/`。

当前是本地候选实现与真实模型样本，不是独立人工业务 Gold 或生产发行。PostgreSQL 已有实现路径，本机 Docker 未运行，未做本轮同资料 PostgreSQL 性能对照；不能宣称迁移数据库的具体提速倍数。


## 本轮真实资料结果

固定原任务的 256 个独立目标，在隔离的一致数据库副本上完成模型推理、关联落库和逐项检查点：

| 版本 | 模型并发配置 | 整体耗时 | 独立模型请求 | 完成目标 |
| --- | ---: | ---: | ---: | ---: |
| 本轮改动前源码 | 32 | 84.894 秒 | 256 | 256 |
| 最终源码，默认配置 | 64 | 31.085 秒 | 256 | 256 |

本轮对照提速 **2.731 倍**。256/256 实际 HTTP 请求体字节一致，模型与 8000 输出上限一致；上下文、候选片段、顺序及独立引用范围一致，无接口错误。它是本轮相对已有优化版本的增益，不能说成“本轮又达到 10 倍”，也不是全项目扫描、HTTP ACK 和所有模型任务的整库端到端结果。

中间版本曾测到 128 并发、64 条保存上限的 27.463 秒，但最终源码默认仍为 64/32；不同迭代及网络尾延迟不能混作严格同版本对比。更大上限未表现出与线程数成比例的收益。

最终保存队列 171 个事务，累计内部处理 **9.176 秒**，提交及退出 **0.774 秒**。本轮定位时同样 256 项的中间版本内部处理曾为约 50.4 秒。**5 秒目标尚未达到**；剩余主要是版本、引用证据与关联对象的逐项装配写入，不能把实际事务提交速度等同全部保存处理速度。这些嵌套阶段与模型网络时间重叠，不能相加当作总耗时。

全部 256 项结构及准确引用核查没有发现违规。另取 20 项做随机 A/B 标签的真实模型盲评，基线/优化平均得分为 14.90/14.95（满分 16）；均无重大问题，基线有 1 项轻微问题、优化没有。此样本未观察到质量下降，但它不是独立人工 Gold 或统计意义上的全面非劣证明；模型随机性仍在，保存数量本身不能当成质量指标。
