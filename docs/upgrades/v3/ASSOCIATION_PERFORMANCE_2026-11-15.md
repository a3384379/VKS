# 扫描与关联性能优化

2026-11-15。目标是同一真实资料、同一模型、完整关联及讲解落库的整体耗时至少缩短至原来的 10%，不减少候选依据、讲解结构或校验。原始 `docs/design/` 保持字节不变。

## 实现与兼容

- 原始任务输入、操作组和逐项检查点继续沿用。生产默认保留原单目标推理、原提示词与完整输出配置，独立请求并行；取消和恢复仍按原目标检查点进行。
- 定向读取当前控件的动作、业务点及准确章节；旧逻辑键和 open_steps 兼容。保存只解析准确原型包和引用所属文档，不为一个目标重建整套关联或验证无关手册闭包。
- SQLite 当前选择映射改由数据库一次聚合为 JSON，每次仍读取当前事务中的完整准确映射，避免每个目标都创建数千个 SQLAlchemy 行对象。PostgreSQL 和冻结 manifest 保留原读取分支；没有新增选择或权限的跨事务缓存。
- 有界缓存仅复用不可变修订、章节映射与派生语料。当前选中版本、实体归属、资料策略、授权及模型设置继续逐次核对；受限读取不复用其他读者的可见性决定。
- 显式合批辅助方法已实现并覆盖独立身份、完整候选、独立引用枚举、完整输出额度、整次实际输入出处继承、部分错误回退及未知传输不重放。真实质量对照发现合批/强化提示版本的过度拒答与注意事项遗漏，因此没有作为生产默认启用，不能把其结构测试称为业务质量通过。
- 浏览器仍为 1–4 路；单路诊断保持串行，其他设置分别允许最多 24/32/32 个模型请求。UI 显示实际请求上限，独立页面任务与旧整批任务共用持久化的 32 请求容量边界。延期发生在 attempt 增加前，不重置原有进度。Broker 发布收尾用状态与 attempt 双重比较，避免覆盖 worker 已登记的短期延期。
- 本地 SQLite 向量评分单独限制并发，减少大量 Python UDF 回调在多线程之间切换；实际 SQL、授权前置过滤、精确余弦分数和排序不变。网络嵌入与讲解请求继续并行，任何数据库写锁都不跨模型网络请求持有。
- 增加三个覆盖索引，既有本地库按需补建；部署库使用 Alembic `t93aeb57c910`。它们只改变访问路径，不改资料、原任务输入、目标分组或检查点格式。
- 扫描按 DOM、加载与布局变化复用提取结果，每文档计算一次弹窗状态；无关时钟不再不断延迟静默判断。仍保持原有最短观察、静默和截止时间。空挂载节点之外已渲染的可见弹窗属于已挂载界面，空白应用继续报告失败。

## 实测方法

主库和向量库使用 SQLite 一致备份，原始任务检查点摘要单独保存。真实模型实验在私有副本中执行，不把合成响应或已有缓存命中作为真实模型完成。既有任务继续运行，部署前另做安全排空及保留性对照。

计时包含逐项读取、检索、模型推理、验证、关联及讲解保存；模型、原始上下文和目标不变，强制真实刷新而非复用答案。初始四页 32 项基线为 206.047 秒；126.314 / 98.220 / 21.172 / 22.265 秒等中间实验均保留，不作为最终达标证据。

进一步分阶段测量发现：32 项的选择映射读取共约 185 次，逐行投影在并发回放中的累计等待约 310 秒；JSON 投影后约 1 秒。这是重叠线程的累计时长，不能当作整批墙钟时长。只读准备也曾占用应用写锁；网络用量登记等待了本不必互斥的全量读取，造成模型槽位空闲。

最终固定样本扩大为八页 64 个操作组。旧实现 64 次请求、360.099 秒；生产默认的原单目标推理仍为 64 次请求，26.198 秒，**13.745 倍**，64 项均有检查点、无请求超时或 429。基线 32 项新保存、32 项不足；优化 30 项新保存、34 项不足。未保存的新回答不删除已有有效说明，不能用新保存数量判断业务质量。

最终版本单项阶段中位数：上下文准备 73.9 ms，既有关联读取 14.3 ms，关键词检索 3.0 ms，向量混合检索 1.260 秒（含本地计算排队），发送前原文/权限复核 27.8 ms。首次文档索引就绪校验 0.405 秒，首次关键词索引构建约 0.4 秒。阶段嵌套并行，不能把中位数或累计时长直接相加为整批耗时；最后一个模型响应到整批完成约 0.098 秒。计时回调只在私有实测脚本启用。

结构检查确认 64 项上下文和完整候选与基线一致、引用属于自己的候选及准确选中版本、已保存讲解和引用与落库一致，结构违规为 0。质量诊断曾发现跨模块套用搜索规则；随后强化提示又出现过度拒答和遗漏注意事项。该尝试的 37 条盲评记录明确标记为失败的诊断版本，已恢复原提示和单目标生成，不以其平均分或计数宣称质量通过。最终原始请求对照与原文盲评另记录验收范围，不代表独立人工 Gold 或全部控件正确性。

最终 64 个实际序列化请求正文与基线逐字节 SHA-256 一致，包含原 `SYSTEM`、JSON Schema、候选顺序/全文摘录、控件上下文与每项 2,500 输出 Token 上限；持久化模型配置指纹也一致。没有通过减少资料、改变推理模型或缩短输出额度换速度。原基线没有单独记录运行时传输配置，因此不把此对照扩大为凭据字节或未记录 HTTP 参数的证明。模型实际回答仍可能随机变化。

上述对照完成后，用户将实际项目输出上限改为 **8,000 Token**，已读取主库确认并保留，没有改回。私有副本补测同一 64 项，所有实际请求的上限均为 8,000，其他请求字段与 2,500 版本 64/64 完全一致；完整耗时 **26.939 秒**、0 请求错误。实际输出中位数为 474.5 Token（2,500 版本为 488），远未触及上限；单次运行的 26.198 / 26.939 秒差异不能证明提高上限必然变慢或变快。8,000 上限没有另跑旧实现同上限基线，13.745 倍数字仍只对应前面的严格同配置对照。补测没有重跑或改写已经完成的原任务。

最终单目标版本的同模型盲评覆盖 64 项：基线较好 19、优化较好 8、相当 37；四项合计均分分别为 14.922 / 14.688（满分 16）。有一项把创建入口与下游支付流程的说明混在一起，属于残留的模型语义边界风险。实际请求完全相同不意味着随机回答逐字一致，也不能据此宣称语义非劣或全部业务正确性已经验收。未通过降低原模型、输入或输出配置换取速度；原有有效说明不会因新回答未保存而删除。
