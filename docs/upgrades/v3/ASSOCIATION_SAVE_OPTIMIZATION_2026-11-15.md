# 关联保存链路后续优化

2026-11-15。接续[并发与异步保存记录](ASSOCIATION_CONCURRENCY_2026-11-15.md)。本轮修改资料核验、依赖读取和批量检查点保存；使用同一原任务的 256 项真实资料及真实模型验证。原任务、检查点和不可变修订保留。

## 实现

- 新增 `input_epoch` 技术版本表。SQLite 触发器覆盖实体、修订、选择、制品和来源快照的变更，包括其他进程及直接 SQL 写入。生成 action/business_point 的正常新增不使资料语料失效；修改、删除采用保守失效。版本使用随机 token，避免事务回滚后重用计数导致缓存错误。
- 每个当前事务先读取资料版本；版本及准确来源集合未变时复用完整资料摘要。文档选择、来源属性或身份变更后重新核验。权限、工作区、模型策略、外部向量设置、任务 attempt/lease/取消及当前目标绑定继续按原规则读取，授权决定不加入跨事务资料缓存。PostgreSQL 保留完整查询分支。
- 保存队列对就绪任务的准确章节及既有业务点合并预取。当前事务内保持 ORM 对象的强引用，减少弱引用释放造成的重复加载；引用范围和人工修改冲突检查继续执行。
- 章节证据合并查询，同一事务复用准确 artifact/digest 身份；关系写入减少中间 flush，仍在保存点及外层提交前执行。预算预留与审计合并刷新，预留真正提交后才发送模型请求。
- SQLite 检查点由提交前回调通过 executemany/upsert 批量写入，冲突时只更新结果，不更换旧检查点身份。进度只在事务提交成功后确认；单项回滚会恢复其待提交进度，外层失败不能确认成功。其他数据库保留原分支。
- 推理只需判断向量存在时使用 `SELECT 1 ... LIMIT 1`；状态统计仍使用完整计数。候选、顺序、提示词和讲解要求不变。
- 默认独立模型请求容量从 64 调整为 128，仍可通过 `VKS_AI_CONCURRENCY` 设置 1–128；浏览器维持 1–4 路，保存批量上限维持 32。API、Worker、Compose 与 Studio 提示保持一致；单路诊断仍串行。没有启用此前质量验证未通过的多控件合并生成。

## 真实资料与模型

| 指标 | 上轮最终版本 | 本轮最终版本 |
| --- | ---: | ---: |
| 目标数 / 实际模型请求数 | 256 / 256 | 256 / 256 |
| 模型并发配置 | 64 | 128 |
| 整体耗时 | 31.085 秒 | 23.229 秒 |
| 保存队列内部累计处理 | 9.176 秒 | 5.526 秒 |
| 保存队列提交及退出累计 | 0.774 秒 | 0.729 秒 |
| 单次 API 中位耗时 | 5.751 秒 | 6.155 秒 |

本轮整体约提速 1.34 倍，保存内部处理减少约 40%。这些累计保存阶段与网络阶段重叠，不能相加作为整体耗时。保存内部仍高于 5 秒；没有达到整库扫描与关联端到端 10 倍的实测证据。

256/256 完整实际 HTTP 请求体字节与上轮一致，模型与 8000 输出上限一致；无接口错误，处理 256 项，保存 146 项，保留 110 项待处理。保存数量受模型随机性影响，不作为质量提高的证明。

全部 256 项上下文、候选顺序、准确引用范围与落库结构核查通过。20 项随机 A/B 标签的同模型盲评：上轮/本轮平均 14.65/14.90（满分 16），均无重大问题；分别有 1/2 项轻微问题。样本没有显示平均质量下降，但存在逐项随机差异；这不是独立人工 Gold 或全面非劣证明。

相同 256 份已保存响应、同为 64 容量的隔离回放中，保存线程 SQL 从 18,965 次减至 12,471 次，查询从 13,754 次减至 7,931 次，有修改的 ORM flush 从 2,679 次减至 1,761 次。输出保持同样的 143 项保存、113 项待处理。回放只用于 SQL 计数和定位，不当作真实模型实测；最终回放与回归并行，不比较其耗时。

资料版本的跨进程失效、SQL 直接修改、回滚 token、授权撤销、批量预取的单项拒绝及批量检查点都有专项验证。SQLite Alembic upgrade/check/downgrade/再 upgrade/check 通过；未运行 PostgreSQL 同资料性能对照。
